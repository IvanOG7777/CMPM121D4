## Target

This game is  a 3D snake game where the player moves a dragon around an enclosed stone map collecting glowing apples. Each apple increases
the dragons length and score by 1. The game uses a smaller 12x12 map with differnt obstacles and layouts, requiring that players avoid walls
and their own body.

## Where things live

The game's rules are stored in the core/ directory, while rendering and player input are handled in the app/ directory.

core/dragon.gd: This file handles dragon movement, growth, and turning.

core/session.gd: Here we take care of food generation, scoring, collisions, and the game's starting and ending conditions.

core/board.gd: Stores the board's tiles and determines whether a tile is solid.

core/kit.gd: This determines which dragon model and rotation should be used for each body segment.

core/level.gd: Finds and loads levels from text files.

app/main.gd: Handles player input, rendering, camera movement, level switching, restarting, and the score display.

app/stage.gd: Handles the environment, lighting, and rendering of the board.

tools/build_art.py: Generates the 3D models using Blender's Python library.

levels/: Contains the text files used to generate each level.

tests/: Contains tests for the game's rules and level parser.

## Adding a tile kind

To add a new tile kind:

Open core/board.gd and add the new tile kind to Board.TILES, specifying whether the tile is solid.

Open tools/build_art.py and create a builder function for the new tile's 3D model.

Register the builder in the TILES dictionary using the same name as the tile kind in core/board.gd.

Open core/level.gd and add a new character to the LEGEND dictionary that represents the new tile.

Add the new character to a text file inside the levels/ directory.

Run deno task art to regenerate the models.

Run deno task dev to check that the tile appears correctly.

Add a test for the new tile's rules and run deno task ci to verify that the changes pass all checks.

## Patterns, and what they bought us

Command Pattern
The Command pattern is used in core/dragon.gd through the turn queue. Player directions are stored before being applied one at a time during each tick.

This prevents multiple quick key presses from causing incorrect movement or allowing the dragon to reverse into itself.

Game Loop Pattern
The Game Loop pattern is used in app/main.gd. The game updates its rules every 0.1 seconds, while the camera updates every frame.

This allows the dragon to move at a consistent speed while keeping the camera movement smooth.

Single Responsibility Principle
Each class has its own responsibility. The Dragon handles movement, the Board handles tiles, the Session handles gameplay rules, and the application handles rendering and input.

This makes the code easier to maintain and test because changes to one responsibility do not necessarily require changes to the others.

## One idea we carried over

One idea that we had decided to carry over was keeping the game rules separate from the framework.

The problem: When gameplay rules and rendering are combined, it becomes harder to test the rules without running the entire game. Changes to the interface may also affect the gameplay logic.

The practice: In our previous TypeScript projects, we separated the game's rules from its rendering and input systems using the core/ and app/ directories. We continued using this structure in D4.

The mechanism: In TypeScript, we separated the rules from the game framework through modules and imports. In Godot, we use RefCounted classes for the core and Node-based classes for the application. This allows us to test the game's rules using Godot's headless mode without opening the game window. Unlike TypeScript, GDScript allows classes to be globally accessible through class_name, so the boundary checker must check for engine-specific dependencies rather than only checking imports.
